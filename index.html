DB 설계의 기초: PK와 데이터 무결성

1. 기본키(Primary Key)의 필요성
테이블에서 각 레코드를 유일하게 식별하기 위해 필요합니다. 식별자가 없다면 데이터가 중복되었을 때 특정 행을 수정하거나 삭제할 수 없는 '데이터 무결성' 문제가 발생합니다. 설계 시에는 값이 변하지 않는 '대리키'를 PK로 선택하는 것이 유리합니다.

2. MySQL AUTO_INCREMENT
일일이 고유한 ID 값을 지정해야 하는 번거로움을 줄여주며, 시스템이 자동으로 중복 없는 값을 생성해 줌으로써 실수를 방지하고 개발 생산성을 높여줍니다.

3. NULL 처리 시 주의점
end_time이 NULL인 경우 '아직 데이터가 없음'을 의미합니다. SQL 조회 시에는 IS NULL을 사용해야 하며, 프론트엔드에서는 사용자에게 그대로 노출하기보다 "미퇴근" 혹은 "-"와 같이 적절한 문구로 치환하여 보여주는 처리가 중요합니다.

4. Crew와 Attendance의 관계
한 명의 크루가 여러 번 출석할 수 있는 '일대다(1:N)' 관계입니다. 이는 일상생활에서 '한 명의 고객과 그 고객이 주문한 여러 건의 내역' 또는 '한 명의 학생과 그 학생이 수강하는 여러 과목'의 관계와 같습니다.

DB 운영 심화: 트랜잭션과 시스템 선택

1. 동시성 요청과 ACID 속성
출석 시스템에서 100명이 동시에 등교 버튼을 누르면 Race Condition(경합 상태)이 발생할 수 있습니다. 이때 트랜잭션의 ACID 속성이 필요합니다.

  • 원자성(Atomicity): 등교 기록 저장과 상태 변경이 '전부 성공'하거나 '전부 실패'함을 보장해 데이터가 꼬이는 것을 막습니다.
  • 격리성(Isolation): 동시에 실행되는 여러 트랜잭션이 서로 간섭하지 못하도록 차단하여, 각 요청이 독립적으로 정확히 처리되게 합니다.

2. 데이터베이스 vs 파일 시스템(CSV)
파일 시스템으로 출석을 관리하면 여러 사용자가 동시에 파일을 수정할 때 데이터가 유실될 위험이 크고 검색 성능이 떨어집니다. 반면 DB는 동시 접근 제어, 데이터 일관성 유지, 세밀한 보안 설정이 가능하여 실제 운영 환경에 필수적입니다.

3. RDBMS vs NoSQL (MongoDB)
구조가 명확하고 관계가 중요한 데이터는 RDBMS(관계형 DB)가 유리합니다. NoSQL은 테이블 대신 JSON 형태의 '문서(Document)' 구조를 사용하여 다음과 같은 특징을 가집니다.

  • 장점: 크루 프로필처럼 필드가 자주 추가되는 유연한 데이터 구조에 대응하기 쉽습니다.
  • 단점: 복잡한 JOIN 연산이나 강력한 데이터 일관성 보장이 상대적으로 어렵습니다.

🔍 DB 설계 심화: 자연키 vs 대리키와 참조 무결성

1. 왜 nickname 대신 ID를 PK로 쓸까?

  • 자연키(Natural Key): 닉네임처럼 실제 비즈니스 의미가 있는 데이터입니다. 하지만 닉네임은 변경될 가능성이 높고, PK가 변경되면 이를 참조하는 모든 외래키(FK)를 수정해야 하는 대공사가 발생합니다.
  • 대리키(Surrogate Key): crew_id처럼 오직 식별만을 위해 생성된 값입니다. 비즈니스 로직과 무관하여 불변성을 유지하기 쉽고 시스템이 훨씬 안정적입니다.

2. 참조 무결성 전략: RESTRICT vs CASCADE

전략 동작 방식 실제 예시
RESTRICT 참조 중인 데이터가 있으면 삭제를 거부 출석 기록이 있는 크루는 탈퇴 불가
CASCADE 부모 삭제 시 자식 데이터도 함께 삭제 크루 탈퇴 시 모든 출석 기록 자동 삭제

🚀 성능과 운영: JOIN, 정규화, 그리고 커넥션 풀

1. 서브쿼리 vs JOIN 성능 차이

  • 서브쿼리 (IN): 가독성은 좋지만, 데이터 양이 많아지면 실행 시마다 쿼리를 평가해야 하거나 최적화가 어려울 수 있습니다.
  • JOIN: DB 엔진(옵티마이저)이 가장 효율적인 경로를 찾기 쉽습니다. 대량의 데이터를 다룰 때는 JOIN이 성능상 훨씬 유리한 경우가 많습니다.

2. 정규화와 비정규화의 트레이드오프

  • 정규화: 중복을 제거해 데이터 일관성을 높입니다. 저장 공간은 아끼지만 조회 시 JOIN이 많아져 느려질 수 있습니다.
  • 비정규화: 의도적으로 중복을 허용해 조회 속도를 높입니다. JOIN을 줄여 성능은 얻지만, 데이터 수정 시 모든 중복 항목을 고쳐야 하는 위험이 있습니다.

3. 연결 풀링(Connection Pooling)의 필요성

DB와 연결을 맺는 과정은 매우 무겁습니다. 미리 연결된 통로(Connection)를 '풀(Pool)'에 담아두고 필요할 때마다 빌려 씀으로써, 수백 명의 동시 접속에도 빠른 응답 속도를 유지할 수 있습니다.

🛠️ 트랜잭션 실무: 원자성(Atomicity)의 실제

Rollback: 실패했을 때의 안전장치

INSERT, UPDATE를 성공했더라도 마지막 DELETE에서 오류가 발생한다면?

  • 결과: 앞선 모든 작업은 취소(Rollback)되어야 합니다.
  • 이유: "반만 성공한 데이터"는 데이터베이스 전체의 신뢰도를 떨어뜨리기 때문입니다. 트랜잭션은 'All or Nothing'을 보장해야 합니다.
